## Executive Summary

A scheduled Splunk detection identified PowerShell execution containing the `EncodedCommand` argument on the domain-joined Windows endpoint. The detection was generated by authorized activity executed specifically to validate the monitoring pipeline.

Rather than treating the alert itself as proof of compromise, I performed an analyst investigation: pivoted from the alert to the raw Sysmon process-creation event, constrained the time window, attributed the activity to a host and user, reviewed the full command line and parent image, examined surrounding process telemetry, removed known collection noise from the analytical view, and compared the remaining evidence with the known test activity.

**Final assessment:** the detection operated as designed and correctly surfaced security-relevant PowerShell behavior. The event was benign because it matched the authorized validation exercise. No evidence in the reviewed telemetry supported escalation to a real compromise.

This distinction is intentional: a detection can be a true positive for the behavior it was designed to identify while the underlying behavior is still authorized.

## Detection Hypothesis

**Hypothesis:** PowerShell launched with encoded-command syntax is sufficiently security-relevant to warrant analyst review because encoding can obscure command content and appears in both legitimate administration and adversary tradecraft.

**Required evidence:** process creation showing PowerShell plus encoded-command syntax.

**Context needed for disposition:** user, host, complete command line, parent process, surrounding processes, timing, and authorization/business context.

## Detection Logic

```spl
index=main "<EventID>1</EventID>" powershell.exe "EncodedCommand"
```

The search was converted into a scheduled alert:
- **Schedule:** every 5 minutes
- **Lookback:** previous 5 minutes
- **Trigger:** result count > 0
- **Severity:** Medium
- **Action:** add to Splunk Triggered Alerts

The alert subsequently appeared in Trigger History, proving the path from endpoint event generation through SIEM alerting.

## Evidence & Findings

### 1. Endpoint and identity attribution
The matching event was tied to:
- **Host:** `DESKTOP-KRAO2L9` / CLIENT01
- **Domain:** `LAB`
- **User:** `LAB\Administrator`
- **Image:** `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`

This established who executed the process and on which monitored endpoint.

### 2. Command-line evidence
The Sysmon process event preserved the PowerShell command line, including `-NoProfile` and `-EncodedCommand`. Command-line telemetry is critical because a process name alone cannot explain intent or behavior.

### 3. Parent-process context
The event also preserved `ParentImage`, allowing process lineage to be reviewed rather than evaluating PowerShell in isolation.

### 4. Surrounding-event correlation
A narrow time-based pivot initially returned 22 Sysmon events. Collection-related Splunk Universal Forwarder helper activity dominated the result set. Filtering known UF image and command-line noise reduced the analytical set to four events and made the controlled PowerShell event easier to evaluate alongside adjacent endpoint activity.

The raw telemetry was not deleted or altered; the filtering occurred only in the search view.

### 5. Alert validation
The scheduled alert appeared in Splunk Trigger History. This validated the complete operational chain:

## Analyst Reasoning

### Why the event deserved investigation
Encoded PowerShell can reduce human readability of a command and is relevant to execution monitoring. MITRE ATT&CK maps PowerShell abuse to **T1059.001**. The presence of encoding increases investigative value, but it does not establish malicious intent by itself.

### Why the event was not escalated
The activity matched the known authorized validation exercise. The scoped telemetry did not show evidence that justified reclassifying the event as an intrusion.

### Why this is still a true positive
The rule was designed to detect encoded PowerShell behavior, and encoded PowerShell behavior occurred. Therefore, the **detection result is a true positive**. The incident disposition is **benign/authorized**.

That distinction prevents two common analytical errors:
1. treating every detection hit as malicious;
2. calling expected activity a false positive when the rule actually detected exactly what it was designed to detect.

## Production Escalation Path

If the same alert appeared without an authorized explanation, I would expand the investigation in this order:

1. Decode and inspect the complete PowerShell payload.
2. Validate the user, endpoint owner, and administrative intent.
3. Examine parent and child process lineage.
4. Correlate nearby authentication events, privilege changes, and remote logons.
5. Search across endpoints for the same encoded payload, command-line fragment, parent process, or user behavior.
6. Review DNS/network activity associated with the process and time window.
7. Check persistence locations and follow-on execution if supported by available telemetry.
8. Escalate to containment if corroborating malicious indicators appear—endpoint isolation, credential protection/reset, evidence preservation, and enterprise-wide scoping according to the IR plan.

## Detection Tuning Opportunities

A production version could be improved by:
- normalizing PowerShell and command-line fields instead of relying on raw XML text;
- matching abbreviated forms such as `-enc` with care;
- adding PowerShell Script Block Logging (Event ID 4104);
- correlating encoded execution with unusual parent processes, network connections, or unsigned binaries;
- suppressing known approved automation only after a documented baseline;
- risk-scoring privileged users and sensitive endpoints more heavily.

## Lessons Learned

- Detection logic and incident disposition are different decisions.
- Narrow time windows reduce analyst noise and improve causal reasoning.
- Parent process and command line materially improve process-event triage.
- Collection tooling can dominate endpoint telemetry and should be tuned analytically rather than deleted.
- A credible report states what the evidence supports—and what it does not.
- Detection validation is incomplete until the analyst can prove the alert fired and explain the resulting event.
